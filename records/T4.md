## 1. The problem T4 solves

So far, everything has been proven against a **mock coordinator inside one EVM**. Gate 5A will create **public state you can't undo**: a Raffle whose subscription ID is `immutable`, a consumer registration, and real LINK spending. T4 answers one question before that:

> *If I broadcast this exact revision, with this config and this key, will the chain end up where I expect? And do I know what to do if it doesn't?*

There are four concrete gaps today:

| Gap                            | Evidence in the repo                                                                                                                                                                                                                                                                                                                    | Consequence if left open                                                                                                                                                                                                       |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **G1 Dangerous config path**   | [DeployRaffle.s.sol:33-42](script/DeployRaffle.s.sol#L33-L42) creates a subscription whenever `subscriptionId == 0`, on any chain. The live ID is `keccak256(msg.sender, blockhash(block.number - 1), coordinator, nonce)` ([SubscriptionAPI.sol:374-380](lib/chainlink-evm/contracts/src/v0.8/vrf/dev/SubscriptionAPI.sol#L374-L380)). | `forge script` computes the ID while simulating at block N. The real create lands in a later block and gets a different ID. The result is an orphan subscription and a Raffle with a **permanently wrong `i_subscriptionId`**. |
| **G2 Silent success**          | The script never checks its own result. Only the local test [DeployRaffleTest.t.sol:37-40](test/integration/DeployRaffleTest.t.sol#L37-L40) does.                                                                                                                                                                                       | A Sepolia simulation can "succeed" while the owner, subscription or consumer is wrong (R9/R16).                                                                                                                                |
| **G3 Assumptions that expire** | VRF parameters, subscription balance and pending requests are a historical snapshot (18 LINK, block `11792671`). `MAX_PLAYERS = 60` is valid only for `callbackGasLimit = 500000` on the measured build (F3).                                                                                                                           | Broadcasting against stale facts. If someone changes the gas limit, the cap stops protecting liveness.                                                                                                                         |
| **G4 No operating procedure**  | Nothing is written for a stalled fulfillment, the F2 rule, teardown, key handling or preserving evidence (`broadcast/` is gitignored, [.gitignore:6](.gitignore#L6)).                                                                                                                                                                   | During an incident you improvise. The owner override is tempting but would invalidate the demo.                                                                                                                                |

**What T4 produces is not a deployment.** It produces a reviewed config, a passing **non-broadcast** simulation and a short runbook. The evidence label stays A/B1, and nothing here counts as C1.

> 中文：至今所有证据都来自单个 EVM 里的 mock。Gate 5A 会产生不可撤销的公开状态，所以 T4 要回答："用这个版本、这个配置、这个 key 广播，链上结果是否如预期？出问题时知道怎么办吗？" 四个缺口：危险的订阅创建路径、脚本不验证自身结果、会过期的假设（含 F3）、没有事故流程。T4 的产出是配置 + 模拟 + runbook，不是部署。

## 2. How it is solved: put each assumption in the cheapest place that fails loudly

| Kind of assumption                                                                 | Mechanism                                                                     | Why                                                                                                |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Config rules that code can check (subId ≠ 0 off-chain, gas limit = measured value) | Revert in HelperConfig/DeployRaffle, plus a local test                        | Fails on every run, including the Sepolia simulation                                               |
| What the deploy actually produced (owner, consumer, coordinator, subId)            | **Post-deploy assertions inside the script**                                  | They run during `forge script` simulation against real chain state, so nobody has to read the logs |
| Chain facts (parameters, balance, pending requests)                                | `cast call` reads, recorded with date and block, plus the re-pinned fork test | Facts change over time, so record *when* each was true                                             |
| Human decisions (budget, interval, teardown, F2, incident steps)                   | A short written runbook                                                       | Code can't decide these                                                                            |

> 中文：能用代码检查的放进代码（会在模拟中自动失败）；链上事实用带区块号的读数记录；人的决策写进 runbook。

## 3. The split

- **Block 1: decisions plus making the script safe, all locally.** D2 and key handling are recorded. The `subscriptionId == 0` guard, the post-deploy assertions and the F3 assertion are added. No RPC, no live transaction, `src/` untouched.
  - **Done when:** the RPC-free suite passes (59 + your new tests), `forge fmt --check` is clean, the mutations below are run and noted, and `git diff f1b3250 -- src foundry.toml` is empty (the build still matches the measured one). Then I start `protocol_test_engineer` for independent verification, and you commit.
- **Block 2: facing the chain, then the final simulation.** Check the official and on-chain VRF parameters. Size the budget. **Create and fund the dedicated subscription. This is the first live transaction, so you do it, after an explicit go-ahead.** Then update the constants as one change set (HelperConfig, HelperConfigTest, fork-test re-pin), write the runbook, and run the fresh simulation.
  - **Done when:** the checklist's T4 Done-when holds ([PENDING_WORK_CHECKLIST.md:188](records/PENDING_WORK_CHECKLIST.md#L188)).

**Why the boundary sits here:** Block 1 needs nothing from the chain. Block 2's constants can't exist until the live subscription exists. The guard must also exist **before** you replace the subscription constant, so a mistaken `0` can't slip through.

> 中文：Block 1 = 本地决策 + 让脚本安全（不碰链、不改 src）；Block 2 = 读链上事实、授权后创建订阅、整组更新常量、runbook、最终模拟。先有 guard 再换常量。

## 4. Block 1 guidance

### Step 0: two decisions (one or two sentences each in the roadmap or records)

1. **D2.** Recommended: a **dedicated subscription** created and owned by a **fresh testnet-only deployer**, so deployer = subscription owner = Raffle owner.
   - Question for you: why does "a dedicated deployer + reusing the old subscription" deploy fine and then fail? Hint: [SubscriptionAPI.sol:427](lib/chainlink-evm/contracts/src/v0.8/vrf/dev/SubscriptionAPI.sol#L427).
2. **Key handling.** Recommended: **keep the env-key path for this milestone.** Converting to `--account` changes the signing interface across HelperConfig, DeployRaffle, Interactions and the zero-key test (which the checklist says not to reopen). Mitigations: a fresh key holding only testnet funds, and `.env` stays ignored ([.gitignore:21](.gitignore#L21)). If you prefer the keystore, Block 1 gets larger. Tell me before you start.

### Task 1.1: the `subscriptionId == 0` guard

Goal: on any chain except 31337, a zero subscription ID reverts **before any broadcast**. Locally, the create-and-fund path still works.

Design questions:
1. **Location.** Should it go in DeployRaffle's `if` branch or in `HelperConfig.getConfigByChainId`? Which one also protects `FundSubscription`/`AddConsumer.*UsingConfig` ([Interactions.s.sol:41-48](script/Interactions.s.sol#L41-L48), [L78-84](script/Interactions.s.sol#L78-L84))?
2. **Ordering.** Should it fail before `getDeployerKey()` reads the environment? Think about what the test then needs, and the principle of failing on config before touching credentials.
3. **Testability.** The Sepolia constant is non-zero, so how do you produce the failing input? Hint: a test-only harness `contract … is HelperConfig` can write the public `networkConfigs` mapping. That tests the rule **and** where it's wired, without editing the production constant.
4. **Error shape.** Use a custom error like the existing `HelperConfig__…` ones. Should it carry `chainId`?

Tests: off-chain with ID 0 reverts with the exact error. The existing local deploy test and Sepolia-config test still pass unchanged. Name tests `test_X_WhenY`.

### Task 1.2: post-deploy assertions (CW-C HIGH, plus F3)

After `addConsumer` in [DeployRaffle.s.sol:57-59](script/DeployRaffle.s.sol#L57-L59), the script itself checks:
- the Raffle is in `getSubscription(subId)` consumers;
- the subscription owner == `vm.addr(deployerKey)` (the D2 alignment);
- `raffle.owner()` == the signer;
- `address(raffle.s_vrfCoordinator())` ([VRFConsumerBaseV2Plus.sol:109](lib/chainlink-evm/contracts/src/v0.8/vrf/dev/VRFConsumerBaseV2Plus.sol#L109)) == the config coordinator, and `getSubscriptionId()` == the config ID;
- **F3:** `getCallbackGasLimit()` == the measured limit.

Design questions:
1. Why read these values **back from the deployed contracts** instead of trusting the constructor arguments you passed?
2. **F3 trap:** if the expected 500000 comes from the same HelperConfig constant, the check is a tautology. Changing the config would change both sides. Where should the "measured" value live, and what comment ties it to the T3.1/D1 measurement?
3. Is reading on-chain state after `vm.stopBroadcast()` fine? Is anything in it sent as a transaction?

### Mutations (run each, note which check fails, then revert it)

- Delete the guard: your harness test must fail.
- Comment out the `addConsumer` call: the script must revert with *your* consumer error.
- Set HelperConfig `CALLBACK_GAS_LIMIT` to `400000`: the script's F3 check must fire, not only HelperConfigTest.
- Make the guard also apply to 31337: the local deploy test must fail.

### Pitfalls

- Don't edit `src/` or `foundry.toml`. The deployed bytecode must stay identical to the build measured at `f1b3250`.
- No bare `vm.expectRevert()`.
- Don't change the Sepolia subscription constant or the fork test yet (that's Block 2).
- `lint_on_build` is on, so new warnings will show up.

Your two decisions, the test names with one sentence each, and the mutation results. Don't commit yet.

**Capability target:** explain without notes why a subscription ID computed during simulation differs from the one on chain, and why the F3 expected value must not come from the config it checks.
