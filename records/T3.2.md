# T3.2: Privilege and request boundaries

## 1. What problem T3.2 solves

Three things in this raffle are trusted or assumed today, but no test proves them.

**Risk 1: a failing VRF request. Does `performUpkeep` leave the raffle half-done?**
- `performUpkeep` writes `s_raffleState = CALCULATING` ([Raffle.sol:137](src/Raffle.sol#L137)) before it calls the coordinator (L138).
- If that call reverts, we rely on the EVM to undo the write. It does, but nothing in the repo tests it.
- If someone later wraps the request in `try/catch`, the raffle would end up `CALCULATING` with no request pending. Entry would be closed and upkeep blocked (`UpkeepNotNeeded`). That is the same stuck state as R3, and the only exit is the owner override.
- A realistic trigger is the Raffle losing its consumer registration on the subscription.

**Risk 2: who may repoint the coordinator.**
- `rawFulfillRandomWords` only accepts the address stored in `s_vrfCoordinator` (`VRFConsumerBaseV2Plus` L143-148).
- `setCoordinator` (L153) decides who can change that address. It allows the owner or the current coordinator, rejects zero, and emits `CoordinatorSet`.
- If that boundary is wrong, a stranger could swap the randomness source, or a mistyped zero would brick the raffle.

**Risk 3: the owner can pick the winner (the R5 and R6 trust assumption).**
- `fulfillRandomWords` ignores `requestId` and the raffle state. It credits the whole pot to `randomWords[0] % players.length` ([Raffle.sol:161-184](src/Raffle.sol#L161-L184)).
- Combine that with the owner-callable `setCoordinator`. The owner points the coordinator at an address it controls, calls `rawFulfillRandomWords` with a chosen word, and takes the pot. This works even while `OPEN` with no request.
- `setCoordinator` is not `virtual`, so it can't be removed without a redesign. We accept it as an owner-trust assumption for this testnet milestone and state it in T5.
- After D1 (cap = 60), a failed callback can still leave the round `CALCULATING` forever (R3). The owner override is then the only exit from that stuck round.
- If this stays unproven, the "owner decides" capability is documented only by someone reading the code. A reader of the demo may think the raffle is trustless, and a future change might remove the exit without anyone noticing.
- Never use the override to complete the live demo.

> 中文：T3.2 处理三个"被信任但没被证明"的点：request 失败时是否整体回滚；谁能改 coordinator；owner 能否选赢家（R5/R6，是被接受的信任假设，也是卡死后唯一的出口）。不证明的后果是：隐藏的 owner 权力只靠阅读代码，没有可执行证据。

## 2. How it is solved: the evidence strategy

Each checklist item becomes an executable test. Each claim is a precise statement about contract behaviour. A test passes or fails, reruns after every change, and can be mutated to check it catches breakage. Reading the code gives you none of these.

| Checklist item            | What the test proves                                                                                                        | What it does NOT prove                                                                                                              |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Request rollback          | With the Raffle deregistered, `performUpkeep` reverts with `InvalidConsumer`, and state, players and balance are unchanged. | Live coordinator behaviour (this uses the mock). The live `InvalidConsumer` path and `PendingRequestExists` rules were not checked. |
| `setCoordinator` boundary | Stranger rejected, zero rejected, owner succeeds with `CoordinatorSet`, old coordinator then rejected.                      | That the library's modifier is correct for every input, or anything about owner key custody.                                        |
| Owner override            | The R5 sequence works in both `CALCULATING` and `OPEN`, and the whole pot is credited and withdrawable.                     | That this is acceptable. It documents the trust assumption and is not a fix.                                                        |

None of this is a security review of the whole contract (that is T3.3), and a passing test is not a security proof.

> 中文：每一项都是对合约行为的精确断言，所以用可执行测试最合适；它们不证明 live coordinator 行为，也不证明"可接受"，只证明"事实如此"。

## Tightening 1: the owner chooses the word, not the coordinator

The coordinator itself never chooses a winner. The chain is:

1. The owner calls `setCoordinator` and points it at an address **the owner controls**.
2. That address calls `rawFulfillRandomWords` with a **word the owner picks**.
3. The contract computes `word % N` and credits the whole pot to that player.

So the owner picks the word, and the word picks the winner. The contract has no way to tell a real VRF word from a chosen one, because it only checks who is calling. It ignores the request ID and the round state, and the OPEN case also skips the interval.

> 中文：不是“coordinator 选赢家”，而是 owner 把 coordinator 指向自己控制的地址，再用这个地址提交自己挑的 word；合约只检查调用者，不检查 word 来源、request ID 或状态。

## Why there are two tests

| Test                  | Situation                                             | What it proves                                                                                                      |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `..._WhenCalculating` | A real `performUpkeep` ran, so a request is pending   | The owner can take over a pending or stuck round. This is the only exit from R3, and it is **not a fair recovery**. |
| `..._WhenOpen`        | No request, interval not passed (`checkUpkeep` false) | The owner can end a round at any time without VRF. This is the full extent of R5/R6.                                |

Together they show the power works whether or not a VRF request exists.

## Tightening 2: "in any situation" has limits

These limits are what the tests establish:
- **Only the owner, or the current coordinator, can do it.** A stranger can't (Block 1).
- **At least one player is required.** With 0 players, `% 0` panics.
- **Only the current round's pot is at stake:** `prize = balance − outstanding`. Earlier winners' claims are untouched.
- **The winner must be in `s_players`.** In practice that isn't much of a limit, because the owner can enter as a player.

What the tests don't prove: that the power is acceptable, how the owner key is protected, or anything about the live coordinator.

> 中文：边界：只有 owner（或当前 coordinator）能做；至少要有 1 个玩家；只能动本轮奖池，不影响之前赢家的 claim；赢家必须在玩家数组里（但 owner 自己可以报名）。测试不证明这种权力“可接受”，也不涉及 live coordinator。

## Why prove a power you aren't fixing

`setCoordinator` comes from the Chainlink base contract and isn't `virtual`, so removing it means redesigning the inheritance. For this milestone it is an **accepted owner-trust assumption**.

Proving it turns "someone read the code and says so" into evidence anyone can rerun. If a later change silently removes the power, the tests fail, and then you know you've also lost the only exit from a stuck round. It also gives T5 and an interview answer something concrete: "this raffle is not trustless; the owner can pick the winner, here is the test."
